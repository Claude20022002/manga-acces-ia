# Session 2026-08-09 — Phase 1 : pipeline Magiv2 → OCR → MangaPage

## Jalon atteint

Pipeline end-to-end fonctionnel, de bout en bout, sur CPU :

```
load Magiv2 → detect() → unload Magiv2 → load manga-ocr → recognize() par bbox → unload manga-ocr → assemble MangaPage
```

Implémenté dans `StructureBackend`/`OCRBackend` (`backends/base.py`, avec `load()`/`unload()`
contractualisés), `Magiv2Backend` (`backends/magiv2_backend.py`), `MangaOCRBackend`
(`backends/manga_ocr_backend.py`) et `PageProcessor` (`pipeline/page_processor.py`,
injection de dépendance des deux backends, sans import direct des implémentations concrètes).

Exécuté avec succès (`exit code 0`) sur `data/manga/test_kitazawa_1902.jpg`, produisant
un `MangaPage` JSON valide (schéma v1 respecté).

## Dépendances cachées de Magiv2 découvertes

Magiv2 (`trust_remote_code=True`) charge en interne ConditionalDETR, TrOCR et ViT-MAE,
dont les dépendances runtime ne sont documentées ni dans le README HuggingFace ni dans
`config.json`. Découvertes une par une, à l'exécution, sur plusieurs itérations :

| Paquet | Découvert via | Raison |
|---|---|---|
| einops | `ImportError` au chargement du module distant | Manipulation de tenseurs (`modelling_magiv2.py`) |
| pulp | idem | Optimisation linéaire (assignation personnages) |
| scipy | idem | `linear_sum_assignment`, calculs internes |
| matplotlib | idem (2e round) | Visualisation (`utils.py`, importé même si non utilisé) |
| shapely | idem | Géométrie des bboxes (`utils.py`, `processing_magiv2.py`) |
| networkx | anticipé par lecture exhaustive des imports avant relance | Graphe d'association texte/personnage (`modelling_magiv2.py`) |
| sentencepiece | `ValueError` tokenizer (diagnostic initial erroné, cf. section transformers) | Suggéré par le message d'erreur transformers, in fine non déterminant seul |
| timm | `ImportError` à l'instanciation de `ConditionalDetrConvEncoder` | Backbone ResNet-50 de ConditionalDETR |

Après le 2e round (matplotlib/shapely), lecture exhaustive de tous les imports
(statiques + inline, ex. deux `from tqdm import tqdm` cachés dans des fonctions de
`modelling_magiv2.py`) des trois fichiers distants (`modelling_magiv2.py`, `utils.py`,
`processing_magiv2.py`) pour anticiper `timm` avant un 3e aller-retour évitable.

Tous déclarés dans `pyproject.toml`, installés automatiquement via `uv sync`.

## Contrainte `transformers<5.0`

`transformers>=4.45.0,<5.0` (borne basse alignée sur la contrainte réelle de `manga-ocr`,
vérifiée via `uv pip show manga-ocr` : `transformers>=4.45.0`, sans plafond côté manga-ocr —
pas de conflit de résolution).

**Cause** : `transformers` 5.x (résolu par défaut en 5.14.1 vu l'absence de plafond initial)
a réécrit l'architecture de tokenizer (`TokenizersBackend`) et casse la conversion
automatique lent→rapide du tokenizer TrOCR interne à Magiv2 (RoBERTa/BPE, `vocab.json` +
`merges.txt`, pas de `tokenizer.json`). Le message d'erreur (`sentencepiece or tiktoken`)
est un fallback générique de `transformers`, pas la vraie cause — vérifié en lisant le
code source de `tokenization_utils_tokenizers.py` : la conversion BPE échoue avant même
d'atteindre la branche sentencepiece/tiktoken. `sentencepiece` a été ajouté sur un premier
diagnostic incomplet ; la vraie cause était la version de `transformers`.

Testé et validé avec `transformers==4.57.6`.

## Mesures de performance (test unique, `test_kitazawa_1902.jpg`, 600×853 px)

- Chargement Magiv2 : **43.46 s**
- Chargement manga-ocr : **3.56 s**

Pas encore de mesure du temps d'inférence pur (`detect()`/`recognize()`) séparé du
chargement — à instrumenter si le temps total par planche devient un sujet en Phase 2.

## Observations — image Kitazawa 1902

- **6 panels détectés**, ordre de lecture cohérent (droite→gauche, haut→bas).
- **5 clusters de personnages** détectés (`character_cluster_labels`), sans nom associé
  (attendu — Magiv2 seul ne nomme pas, cf. `Character.name = None` en Phase 1).
- **1 seul élément de texte reconnu** sur toute la planche (`"ならねえからお」"`, panel-2).
  Les 5 autres panels n'ont aucun texte associé. Deux hypothèses non tranchées : Magiv2
  n'a détecté qu'une bbox de texte au total sur cette image, ou d'autres bboxes détectées
  avaient leur centre hors de tout panel et ont été silencieusement ignorées (comportement
  accepté en Phase 1, à logger en Phase 2 — cf. commentaire dans `page_processor.py`).
  Cohérent avec l'observation de la baseline Phase 0 : ce strip de 1902 est hors
  distribution d'entraînement des modèles (manga-ocr et probablement Magiv2, entraînés sur
  du manga imprimé moderne) — pas une preuve de bug, pas non plus une preuve de qualité.
