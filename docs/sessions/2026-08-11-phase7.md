# Session 2026-08-11 — Phase 7, voix distinctes et Manga109-s

## Jalon

Voix japonaises distinctes par personnage, prononciation correcte via
misaki/pyopenjtalk.

## Difficultés rencontrées et solutions

### 1. kokoro-onnx ne supporte pas le japonais nativement

- Symptôme : `"in Chinese ya let"` / `"in Japanese ya let"` dans l'audio
  pour tout texte japonais contenant des kanji.
- Cause : le tokenizer de kokoro-onnx (`kokoro_onnx.tokenizer.Tokenizer`)
  phonémise exclusivement via `phonemizer-fork` (espeak-ng). espeak-ng
  1.52.0 gère correctement le kana pur mais pas les kanji — dès qu'il
  rencontre un kanji hors de son petit dictionnaire (ex. `腹` seul),
  il émet un artefact `(en)Chinese(ja)...` au lieu d'un phonème, qui se
  retrouve tel quel dans le flux audio. Confirmé en isolant le caractère
  fautif et en testant `espeak-ng` en ligne de commande directement (même
  résultat, donc pas un bug du wrapper Python).
- Tentatives sans effet : installation de `misaki[ja]`, changement de
  `lang`, changement de voix — aucun effet, car **kokoro-onnx (0.5.0,
  dernière version) n'appelle misaki nulle part dans son code** ; c'est
  à l'application appelante de le faire (confirmé par lecture du code
  source installé + README GitHub du projet).
- Solution : intégrer misaki/pyopenjtalk directement dans
  `KokoroBackend.synthesize()` via `Kokoro.create(..., is_phonemes=True)`
  (paramètre existant de kokoro-onnx, prévu pour ce cas d'usage) :
  `JAG2P(version="pyopenjtalk")` phonémise le texte japonais, on ne garde
  que la première moitié de la chaîne retournée (les deux moitiés,
  phonèmes puis tonalité, ont une longueur égale garantie par
  construction dans `misaki/ja.py`), puis on passe le résultat à Kokoro.

### 2. speaker_id jamais renseigné

- Symptôme : tous les dialogues utilisaient la même voix
  (`VOICE_UNKNOWN = jf_nezumi`), le pool de voix par personnage
  n'était jamais atteint en pratique.
- Cause : `page_processor.py` n'exploitait pas
  `text_character_associations`, pourtant déjà retourné par
  `Magiv2Backend.detect()` (`predict_detections_and_associations`).
- Solution : câblage `text_idx -> char_idx -> cluster_id` dans
  `PageProcessor.process()`, juste après chaque `recognize()` — renseigne
  `TextElement.speaker_id = f"char-{character_cluster_labels[char_idx]}"`.

### 3. Voix distinctes par personnage

- Pool japonais : `jf_alpha`, `jf_gongitsune`, `jm_kumo`.
- Assignation déterministe : `cluster_id % 3` (même cluster -> même voix
  à chaque run).
- Narrateur : `jf_tebukuro`. Inconnu/`speaker_id` non résolu : `jf_nezumi`.

### 4. Écosystème Python 3.14 : le package `kokoro` officiel écarté

Vérifié via les métadonnées PyPI (pas testé par installation) :

- Le package officiel `kokoro` (v0.9.4) déclare `torch`, `transformers`
  et `misaki[en]>=0.9.4` comme dépendances — `torch`/`transformers` sont
  précisément les dépendances lourdes que CLAUDE.md demande de ne pas
  installer sans validation explicite, en plus d'aller à l'encontre de la
  contrainte CPU/12 Go RAM du projet.
- `spacy` (dépendance transitive possible de la chaîne misaki/cutlet,
  cf. issue GitHub thewh1teagle/kokoro-onnx#147) ne publie des wheels
  précompilées que jusqu'à `cp313` — aucune pour `cp314`, la version
  Python de ce projet. Une installation forcerait une compilation source.
- kokoro-onnx + `misaki[ja]` en mode `pyopenjtalk` (plutôt que le mode
  `cutlet` par défaut, qui dépend de `fugashi`/`unidic` et nécessite un
  téléchargement de dictionnaire séparé non automatique) évite ces deux
  écueils : aucune dépendance lourde, aucun besoin de wheel `cp314`.

## Benchmark Manga109-s

- 10 pages sélectionnées manuellement (2 par genre inféré du titre —
  action, romance, comédie, sport, fantastique — via `ARMS`,
  `LoveHina_vol01`, `TennenSenshiG`, `UltraEleven`, `GinNoChimera`),
  triées par densité de texte depuis les annotations XML.
- 9/10 pages OK. 1 échec (`LoveHina_vol01_055.jpg`, `index 510 is out of
  bounds for axis 0 with size 510`) causé par un segment de texte trop
  long dépassant la limite phonèmes de Kokoro — corrigé par une
  troncature préventive `_MAX_CHARS = 200` dans `KokoroBackend.synthesize()`.
- Moyennes (pages OK) : 10.7 panels/page, 29.1 textes/page — nettement
  plus dense que le corpus `data/manga_jpg` utilisé jusqu'ici (5.4
  textes/page en moyenne sur `data/outputs/benchmark_corpus.csv`, soit
  un facteur ~5,4×). Le pipeline tient sur des planches réelles et
  denses, sans régression liée à la charge.

## Résultat final

Pipeline complet fonctionnel :

- Japonais : `jf_alpha`/`jf_gongitsune`/`jm_kumo` par personnage
  (`cluster_id % 3`), phonémisation misaki/pyopenjtalk.
- Français : `ff_siwis` (descriptions Qwen3-VL).
- SFX / narrateur : `jf_tebukuro`.
- Prononciation japonaise correcte via misaki/pyopenjtalk (espeak-ng
  écarté pour le japonais — kanji non supportés).

Non vérifié dans cette session : qualité perçue à l'oreille de la
prononciation (aucun outil d'écoute disponible côté agent) — validation
humaine encore à faire sur `data/outputs/test_misaki_ja.wav`.
